# Cloudflare Certificate Automation Plugin — with Universal SSL / Advanced Certificate support

> **This is the "managed support" variant** of `../cloudflare-automation-plugin`. It is a copy of
> that plugin (artifact `cloudflare-automation-plugin-managed-support`, same TLM entry point
> `CloudflareAutomationPlugin`) extended so that certificates **Cloudflare issued itself** —
> Universal SSL and Advanced Certificate Manager (ACM) certificates from Google Trust Services,
> Let's Encrypt or SSL.com — are discovered as assets and can be **replaced by a custom (DigiCert)
> certificate** from TLM. The original plugin is left untouched; everything below that is not in the
> section *Switching from a Cloudflare-managed certificate* behaves exactly as there.

A Java-based automation plugin for DigiCert **Trust Lifecycle Manager (TLM)** that manages the
lifecycle of **custom certificates in one Cloudflare zone** over the Cloudflare v4 API. It
discovers the custom certificates uploaded to the zone **and the Cloudflare-managed certificates
serving it**, has the key pair and CSR generated by Cloudflare (default) or on the TLM sensor,
installs the CA-signed certificate by updating the existing custom certificate in place (default),
by uploading a new one and retiring the old one, or — for a Cloudflare-managed certificate — by
uploading a custom certificate in its place and optionally retiring the managed one, and validates
the result — all driven by TLM.

It is a port of the FortiGate automation plugin (same SDK skeleton, PAM support, packaging and
replacement-resolution logic) onto the Cloudflare API surface used by the DigiCert post-enrollment
scripts in `../../AWR-Script`:

| Script | What it does | Plugin equivalent |
|---|---|---|
| `csr-in-cloudflare-api.sh` | Cloudflare generates the CSR (`POST /custom_csrs`), DigiCert ONE issues, upload with `custom_csr_id`, delete matching old certificates, CSR retention | CSR mode **Cloudflare** + renewal strategy **replace_delete** + *CSRs to keep* |
| `csr_in_digicert_awr.sh` / `.ps1` | TLM post-script: upload the issued certificate + private key (leaf + ICA for `force`), delete matching old certificates | CSR mode **sensor** + renewal strategy **replace_delete** |

What the plugin adds on top of the scripts is **discovery** (every custom certificate becomes a
selectable asset in TLM), **update in place** (the Cloudflare certificate id, priority and
settings survive a renewal) and, in this variant, the **Google/Let's Encrypt → DigiCert switch**
(a Universal or Advanced certificate becomes a selectable asset; requesting a certificate for it
uploads a custom certificate and hands the hostnames over).

> API (37 tests: the 25 of the base plugin plus 12 for certificate-pack discovery, managed
> replacement resolution, hostname coverage, Universal SSL disable / pack delete, deferred
> retirement, keep mode and the guard that never rotates a pack through `/custom_certificates`).
> The shaded jar passes the SdkRuntime classpath scan and an eager load of every plugin class.
> Discovery of packs and the switch from an Advanced (Google) certificate to a DigiCert custom
> certificate were driven from TLM against a real zone on 2026-10-23 (see *Tested with*); the

> it checks, read-only and with a PASS/WARN/FAIL per item, that every piece of data the plugin

The plugin extends `AbstractAutomationWorkflow` and implements the five TLM lifecycle operations:

| Operation | Cloudflare API action |
|---|---|
| `testConnection` | `GET /user/tokens/verify` (token active), `GET /zones/{zone}` (zone readable), `GET /zones/{zone}/custom_certificates` (SSL permission); informational: `GET /ssl/certificate_packs`, `/ssl/universal/settings`, `/acm/total_tls` |
| `refreshConfiguration` | `GET /zones/{zone}/custom_certificates` (all pages) **and** `GET /zones/{zone}/ssl/certificate_packs?status=all` (types `universal`, `advanced`, `total_tls`; unless the connector says *ignore*) → one endpoint per certificate; certificate body fetched by a **TLS handshake against the Cloudflare edge** (see *Certificate bodies*) |
| `generateCsr` | **Cloudflare mode:** `POST /zones/{zone}/custom_csrs` — Cloudflare generates the key pair, keeps the private key, returns the CSR and an id. **Sensor mode:** key pair + PKCS#10 CSR generated on the sensor; the private key is retained in the flow directory |
| `installCertificate` | identify the certificate to replace (alias → thumbprint → endpoint → hosts; custom certificates first, Cloudflare-managed second) → **update:** `PATCH /zones/{zone}/custom_certificates/{id}` with the certificate and `custom_csr_id` / `private_key`; **replace:** `POST /zones/{zone}/custom_certificates` then `DELETE` (or keep) the replaced one; **managed:** `POST /zones/{zone}/custom_certificates`, then keep the managed certificate or retire it (`PATCH /ssl/universal/settings {"enabled":false}` for Universal, `DELETE /ssl/certificate_packs/{id}` for Advanced / Total TLS) → wait for `status: active` → CSR retention clean-up |
| `validateCertificate` | `GET /zones/{zone}/custom_certificates/{id}`: present, `active`, `expires_on` equals the issued certificate's notAfter; best-effort edge probe compares the served serial; completes a retirement the install deferred because the custom certificate was still `pending` |

## Architecture

```
TLM  ──JSON──►  CloudflareAutomationPlugin        (SDK entry point: the 5 lifecycle methods)
                        │  builds AdapterConfig, resolves the certificate to replace, stable endpoints
                        ▼
                CloudflareAdapter                 (all Cloudflare logic; returns Result<T>)
                        │
                        │ CloudflareRestClient  (Bearer token, JDK trust store, retry on 429/5xx)
                        ▼
       https://api.cloudflare.com/client/v4/zones/{zone}/{custom_certificates,custom_csrs}
       https://api.cloudflare.com/client/v4/zones/{zone}/{ssl/certificate_packs,ssl/universal/settings,acm/total_tls}
       + TLS handshakes to <host>:443 on the Cloudflare edge for certificate bodies
```

- **Authentication.** Every call carries `Authorization: Bearer <API token>`. The token needs
  **Zone → SSL and Certificates → Edit** and **Zone → Zone → Read**, scoped to the zone. It is
  never logged.
- **TLS to the API** uses the JDK default trust store (Cloudflare presents a publicly trusted
  certificate); JVM proxy system properties are honoured. The edge probes are trust-all because
  they only read the served certificate.
- **Cloudflare error reporting.** Every response is an envelope with `success`, `errors[{code,
  message}]`, `result`, `result_info`; the plugin treats `success: false` as a failure even inside a
  2xx and surfaces the error codes in the TLM error message. 429 / 5xx are retried once.
- **Private key custody.** *Cloudflare mode* (default): the key never leaves Cloudflare; the CSR id
  is persisted in the flow record (`<java.io.tmpdir>/CloudflareAutomationPlugin/<flowId>/flow.json`)
  between `generateCsr` and `installCertificate`. *Sensor mode*: the PKCS#8 key is kept
  owner-readable at `<flow dir>/request.key` and deleted as soon as the upload succeeds. In both
  modes `generateCsr` and `installCertificate` must run on the **same sensor** (each call is a
  fresh JVM).

## The "replace the existing certificate" use case

1. `refreshConfiguration` discovers every custom certificate in the zone as a selectable asset,
   carrying its Cloudflare **id** (round-tripped as the asset alias), hosts, issuer, status,
   expiry and — when the edge probe succeeds — the certificate body.
2. The operator selects the discovered certificate in TLM and requests a certificate for it. TLM
   round-trips the asset identity in `virtualServerName` as `<partition>/<id>`, and on install also
   sends `currentCertificateThumbprint` and the endpoint `ipAddress`.
3. `generateCsr` creates the CSR (Cloudflare or sensor) and returns it; TLM has it signed.
4. `installCertificate`:
   0. identifies the certificate to replace (see *Which certificate gets replaced*);
   1. **update** (default): `PATCH`es that certificate with the new chain and key reference in one
      call. **Cloudflare answers with a new certificate id and the old record is gone at once**
      (observed live 2026-10-12; the schema does not say so). The plugin tracks the returned id from
      then on and deletes the old record if it unexpectedly survives. If Cloudflare refuses the
      PATCH, the plugin falls back to upload + delete and says so in the log;
   2. **replace_delete** / **replace_keep**: `POST`s a new custom certificate with the connector's
      *Certificate type* and *Chain bundling*, waits for it to become `active`, then deletes (or
      keeps) the replaced one(s);
   3. in Cloudflare CSR mode, deletes older Cloudflare CSR records for the same common name beyond
      the configured retention (the CSR just used is always kept).
   4. once Cloudflare reports the certificate `active`, probes the edge and logs the **serial it now
      serves** next to the serial TLM issued (Cloudflare's API never returns a serial; the edge does).
5. `validateCertificate` confirms the custom certificate is `active` and that its `expires_on`
   equals the issued certificate's notAfter (Cloudflare never returns the body or serial, so expiry
   is the identity check); the edge is probed and a different served serial is logged as a warning
   (propagation / overlapping certificate), not failed.

**On a TLM retry** the plugin recognises a certificate that already carries the issued leaf (same
expiry, overlapping hosts) and only completes the retirement of the replaced one.

## Switching from a Cloudflare-managed certificate (Universal SSL / Advanced) to DigiCert

Cloudflare issues Universal SSL and Advanced Certificate Manager certificates through **Google
Trust Services, Let's Encrypt or SSL.com** and does not let a customer choose another CA. The only
way to serve a DigiCert certificate on the Cloudflare edge is a **custom certificate** (Business or
Enterprise plan). Cloudflare then picks the certificate it serves for a hostname by, in order,
*hostname specificity* (an exact name beats a wildcard), *certificate type* (Custom Legacy > Custom
Modern > Advanced > Universal) and expiry — so a custom certificate wins over a Universal or
Advanced one for every hostname it names at least as specifically.

What this variant does with that:

1. **Discovery** lists the zone's certificate packs (`GET /ssl/certificate_packs?status=all`) and
   surfaces every pack of type `universal`, `advanced` or `total_tls` as an asset, next to the
   custom certificates. The alias is **`pack-<pack id>`**; hosts, status, CA, issuer and the expiry
   of the pack's primary certificate come from the API, the body from an edge probe (a Universal
   pack carries an ECDSA and an RSA certificate with different expiries — the probe accepts either).
   TLM therefore shows the Google-issued certificate on, say, `example.com:443`.
2. The operator **requests a certificate for that asset** in TLM, with a profile whose CN/SANs
   cover the hostnames the DigiCert certificate should take over.
3. `generateCsr` works as usual (Cloudflare or sensor key).
4. `installCertificate` resolves the alias to a *managed* replacement — the resolver never treats a
   pack id as a custom-certificate target, so nothing is `PATCH`ed or `DELETE`d under
   `/custom_certificates` — and **uploads a new custom certificate** (`POST`, with the connector's
   certificate type and chain bundling). Then, per the connector setting *Cloudflare-managed
   certificates*:
   - **`discover_keep`** (default): the managed certificate stays. Cloudflare serves the custom
     certificate for every hostname both cover and keeps the managed one as fallback for the rest.
     The log lists exact pack hostnames the custom certificate covers only through a wildcard —
     Cloudflare keeps serving the managed certificate for those (specificity beats type).
   - **`discover_retire`**: once the custom certificate is `active` **and covers every hostname of
     the pack** (a wildcard pack host needs the same wildcard in the new certificate), a Universal
     pack is retired by **disabling Universal SSL** (`PATCH /ssl/universal/settings`) and an
     Advanced / Total TLS pack by **deleting it** (`DELETE /ssl/certificate_packs/{id}`). If a pack
     hostname is not covered the pack is kept and the log says which hostname to add to the profile.
     If the custom certificate is still `pending`, the retirement is parked in the flow record and
     **completed by `validateCertificate`** once it is active.
   - **`ignore`**: behaves like the base plugin (custom certificates only).
5. `validateCertificate` validates the custom certificate that replaced the pack (the flow record
   points at it; when the record is missing the plugin finds it by endpoint or serial) and warns
   when the edge still serves another serial.

After the switch, discovery reports the **custom certificate on the plain hostname endpoint** and
a kept pack where it always was (`universal.<host>:443`, `advanced-<id prefix>.<host>:443`); a
retired one disappears.

**Total TLS** (an ACM feature that orders a hostname-specific Advanced certificate for every proxied
record) is never changed by the plugin, but discovery, the install and the handover log a `WARN`
when it is enabled, because those exact-name certificates outrank a wildcard custom certificate.

**What to check before switching a production zone**

- The zone plan allows custom certificates (Business / Enterprise).
- The TLM profile names every hostname the managed certificate serves that should move — ideally
  as exact names; a wildcard-only DigiCert certificate is outranked by exact-name Advanced / Total
  TLS certificates.
- Keep `discover_keep` for the first switch and look at the edge probe in the install log; move to
  `discover_retire` once the custom certificate is confirmed served. Disabling Universal SSL is
  immediate and zone-wide: every hostname without an active custom or Advanced certificate loses
  HTTPS, and Cloudflare features that depend on it (HSTS, Always Use HTTPS, HTTPS redirects) can
  error.
- The API token needs *Zone → SSL and Certificates → Edit* (it covers packs and the Universal SSL
  setting too).

### Which certificate gets replaced

`ReplacementResolver` picks the certificate(s) to retire through a chain, accepting only ids that
**exist in the zone**, and logs which rule matched:

1. an explicit `certificateName` extended-request field (user override), else
2. the `virtualServerName` alias (`<partition>/<id>` or `<partition>/pack-<id>`), else
3. the **`currentCertificateThumbprint`** TLM sends, matched against the certificate bodies fetched
   from the edge, else
4. the **endpoint**: the certificate whose discovery endpoint equals the request's `ipAddress`, else
5. **host coverage**: certificates whose `hosts` cover the new leaf's CN or one of its SAN DNS names
   (wildcards honoured), with the same key algorithm when the body is known (an RSA renewal never
   selects an ECDSA certificate), newest first.

Every rule looks at **custom certificates first and Cloudflare-managed packs second**; a managed
match is returned separately (`managedIds`) and only ever leads to an upload plus handover, never to
a `PATCH`/`DELETE` of a custom certificate (the key-algorithm filter does not apply to managed
matches: moving from Cloudflare's ECDSA certificate to an RSA DigiCert certificate is a normal
switch). If nothing matches, a new custom certificate is uploaded and a `WARN` explains that nothing
was replaced. With *update in place* only the first match is PATCHed; further matches are left alone
and listed in the log.

## Asset discovery & the endpoint model

TLM's automation inventory is **endpoint-centric** — a certificate renders only when anchored to a
data `IP:port`. Each certificate — custom or Cloudflare-managed — becomes one endpoint:

```
<primary host>:443          e.g. www.example.com:443
```

- **Primary host** = the subject CN when it is among the hosts, else the shortest non-wildcard host,
  else `wildcard.<base>` for a wildcard-only certificate, else `cert-<id prefix>.<zone>`.
- **The plain hostname is reserved for custom certificates.** It is stable across renewals (the
  id is not part of the endpoint); when several custom certificates share the primary host (an
  RSA/ECDSA pair, legacy + SNI, a kept predecessor) the one expiring last owns it and the others are
  reported on `<id prefix>.<host>:443`.
- **Cloudflare-managed certificates get a stable, self-describing location** that never changes
  with what else is in the zone: `universal.<host>:443` for the Universal pack,
  `advanced-<id prefix>.<host>:443` and `totaltls-<id prefix>.<host>:443` for the others (an id
  suffix is added when a label would collide). The TLM location therefore tells you what the object
  is, and a switch from a managed to a custom certificate never makes a different certificate show
  up under the location TLM installed to (seen 2026-10-23: the Universal certificate took over the
  plain hostname after the custom certificate was deleted and looked like the TLM-issued one).
- `alias` / `serverParam` = the Cloudflare custom certificate id, or `pack-<pack id>` for a
  Cloudflare-managed certificate (round-trips as `virtualServerName`). `partition` is `default`,
  `portWithCert` is `443:<alias>`, `peerInfo` is `<zone>:PRIMARY` — the fields other TLM plugins
  populate and the TLM UI reads (left null, TLM composed `null/<alias>`).
- `domainName` = the subject CN when the body is known, else the primary host. `managementIp` /
  `hostName` = the zone name; `osName` = `CLOUDFLARE`.
- Every custom certificate is surfaced — expired and pending ones included (they are what an
  operator wants to replace); `deleted` ones are skipped. Cloudflare-managed certificate packs of
  type `universal`, `advanced` and `total_tls` are surfaced too (unless the connector says
  *ignore*); packs of other types (`sni_custom`, `legacy_custom`, `keyless`, SaaS) are skipped
  because custom certificates already come from `/custom_certificates`. TLM cannot *renew* a managed
  certificate — requesting a certificate for it means *replacing* it with a custom one.

### Certificate bodies

Cloudflare's API **never returns the PEM** of a custom certificate (only hosts, issuer, signature
algorithm, status, expiry, priority), and TLM only inventories a certificate when it receives the
body. The plugin therefore performs TLS handshakes against the Cloudflare edge, in order: each
non-wildcard host directly; the same hosts via the zone apex address with SNI (covers DNS-only
records); for wildcard hosts `www.<base>` and `<base>`. The served certificate is accepted when its
**notAfter equals Cloudflare's `expires_on`** and at least one name overlaps the listed hosts. All
probes share a 20-second budget per discovery (`CLOUDFLARE_PROBE_BUDGET_MILLIS` overrides it);
certificates whose body cannot be fetched are surfaced with metadata only, and the log says so.
The body handed to TLM is the **whole chain the edge serves** (leaf first, then the intermediates),
the way other discovery plugins deliver it, so TLM never has to fetch an issuer itself. For a
managed pack the served certificate is accepted when its notAfter equals the expiry of **any**
certificate in the pack; a Universal pack holds an RSA and an ECDSA leaf and the probe returns the
one the edge negotiates (ECDSA for every modern client), which is what Cloudflare labels by its
signature algorithm, e.g. "ECDSA SHA384". Reasons a probe can miss: the certificate is `pending`/`expired` (not
served), another certificate with higher priority (a custom one over a managed one) is served for
that host, the host is not proxied through Cloudflare, or the sensor has no outbound 443 to the edge.

## Connector configuration (TLM)

Defined in `configuration.json` and surfaced in the TLM connector UI:

| Field | Type | Notes |
|---|---|---|
| Managing sensor | select | Dynamic TLM list (`options_provider: Sensors`) |
| Cloudflare Zone ID | input | 32 hex characters (zone Overview → API). Unique key of the connector; one connector per zone |
| Authentication method | select | *Self-authentication (Direct input)* (default) or *Self-authentication (Secrets manager)* |
| Cloudflare API token | password | Direct-input mode only. Stored by TLM as a sensitive credential (`config_attributes.password`) |
| Secrets manager connector | select | Secrets-manager mode only. Dynamic TLM list of registered PAM connectors |
| Cloudflare API token (PAM vault reference) | input | Secrets-manager mode only. The **vault reference** the PAM connector resolves at runtime |
| Private key and CSR generation | select | `cloudflare` (default; RSA 2048 / ECDSA P-256 only) or `sensor` (any key size) |
| CSR subject fallback (C, ST, L, O) | input | Cloudflare CSRs require all four; the TLM profile's subject DN wins, this fills gaps. Default `C=US, ST=Utah, L=Lehi, O=DigiCert` |
| How a renewed certificate replaces the existing one | select | `update` (default), `replace_delete`, `replace_keep` |
| Certificate type for new uploads | select | `sni_custom` (default) or `legacy_custom`; only used by `POST`, an update keeps the existing type |
| Chain bundling | select | `force` (default: leaf + issuing CA as issued; works with private CAs), `ubiquitous`, `optimal` (leaf only; CA must be publicly trusted) |
| Cloudflare-managed certificates (Universal SSL / Advanced) | select | `discover_keep` (default: list them as assets; after a switch keep them as fallback), `discover_retire` (after a switch disable Universal SSL / delete the Advanced pack once the custom certificate is active and covers all its hostnames), `ignore` (custom certificates only, like the base plugin) |
| Cloudflare CSRs to keep per common name | input | Default 5; retention clean-up after a successful install in Cloudflare CSR mode |

**Every field is declared required** (`optional: false` + `requiredRule`) with a default value where
one makes sense: the TLM connector form answered "Server error" on add/edit while fields were
declared optional (FortiGate plugin, 2026-09-22). The two *API token* rows are the **same**
`config_attributes.password` field declared twice with a different `type` and a `conditional_group`,
so exactly one is shown depending on the authentication method. Keeping the token in the `password`
field is what makes TLM's sensitive storage and PAM injection work unchanged.

### Secrets Manager (PAM) authentication

Identical to the FortiGate / FortiWeb / Azure Key Vault plugins: the connector stores only a vault
reference; at run time TLM asks the selected PAM connector (BeyondTrust Password Safe, CyberArk CCP,
Delinea Secret Server / Platform) to resolve it and injects the real token into `password`. The
plugin **fails closed** when no value arrives. Directly-typed secrets arrive base64-encoded from TLM
and are decoded only when the decoded bytes are printable text; a raw Cloudflare token contains `_`
and `-`, which are not base64 characters, so it is used unchanged (covered by a unit test).

### Cloudflare prerequisites

- The zone must be on a plan that allows **custom certificates** (Business or Enterprise). On other
  plans the upload fails with a plan/entitlement error, which the plugin reports.
- An **API token** (My Profile → API Tokens → Create Token) with *Zone → SSL and Certificates →
  Edit* and *Zone → Zone → Read*, zone resource limited to the zone. The token is shown once.
  *SSL and Certificates → Edit* also covers `ssl/certificate_packs`, `ssl/universal/settings` and
  `acm/total_tls`; a token without it still works with the connector set to *ignore*.
- The sensor needs outbound HTTPS to `api.cloudflare.com` (and, for certificate bodies, to the
  zone's hostnames on the Cloudflare edge).
- *Cloudflare CSR mode* supports **RSA 2048 and ECDSA P-256 only**; a TLM profile asking for another
  size is mapped to the nearest supported type with a warning (the CA enforces the profile's key
  policy at enrollment). Use *sensor* mode for RSA 3072/4096 or P-384.
- Cloudflare CSRs require **country, state, locality and organization**; make sure the TLM
  certificate profile's subject DN carries them or set the connector's fallback.
- Intermediate CA: with `force` the plugin uploads leaf + issuing CA exactly as TLM issued them, so
  nothing has to be pre-configured in Cloudflare.

## Building

```bash
export GITHUB_ACTOR=<your-github-username>
export GITHUB_TOKEN=<token-with-read:packages>
./build.sh           # or: mvn clean package -s settings.xml -U
```

Artifacts:
- `target/cloudflare-automation-plugin-managed-support-1.0.0.jar` — fat (shaded) JAR
- `plugin-dist/cloudflare-automation-plugin-managed-support-1.0.0.zip` — TLM distribution package (jar + `plugin-meta.json`)
- `plugin-dist/checksums` — SHA-256 checksum

The plugin name in `plugin-meta.json` is the artifact id, so this variant can be uploaded to TLM
next to the base plugin; both register the same `CloudflareAutomationPlugin` entry point and share
the flow directory on a sensor (flow ids are unique, so that is harmless).

The fat JAR is built with the **Maven Shade plugin**; jar signatures are stripped. The TLM
`SdkRuntime` eagerly loads every class on the classpath at startup; the packaged jar has been
verified to load all of its classes without a `NoClassDefFoundError`. Re-verify after any dependency
bump (`java -jar target/cloudflare-automation-plugin-managed-support-1.0.0.jar </dev/null` must fail
only with "plugin-info.json does not exists").

## Notes & limitations

- **One zone per connector.** The zone id is the unique key. Account-wide discovery across zones
  is not implemented (the token verify / zones list calls would allow it later).
- **Same sensor for CSR and install.** The flow record (and, in sensor mode, the private key) lives
  in the sensor's temp directory between the two calls.
- **Update strategy changes the id.** A `PATCH` makes Cloudflare re-issue the custom certificate
  under a new id (priority and type are expected to carry over, not yet confirmed). The TLM
  endpoint is host-based, so TLM keeps tracking one endpoint; the alias simply changes at the next
  discovery.
- **Certificate type.** Cloudflare's schema omits `type` but the live API returns it; discovery
  uses it (`isSni` false only for `legacy_custom`). An in-place update keeps the existing type.
- **Overlapping certificates.** With `replace_keep` the previous certificate stays in the zone and
  Cloudflare decides which one it serves by type/priority; the plugin does not call the
  `prioritize` endpoint (the runbook can).
- **Edge probes** are best effort and bounded by the probe budget; a certificate without a body is
  still discovered but TLM will not show it as an inventoried certificate until a body is obtained.
- **Timing.** TLM re-dispatches an action that stays silent for ~60 s; the plugin bounds probes
  (20 s), activation polling (12 s) and API timeouts (60 s) accordingly.
- **Geo restrictions / policy / keyless SSL** attributes are left untouched by updates and not set
  on uploads.
- **`POST /custom_certificates` (replace strategies and the managed switch) not yet exercised
  live.** `PATCH` with `custom_csr_id` is confirmed from TLM (see *Tested with*); the upload path is
  the same body plus `type` and is covered by the mock tests only.
- **Managed-certificate API surface mocked only.** `GET /ssl/certificate_packs?status=all`,
  `PATCH /ssl/universal/settings`, `DELETE /ssl/certificate_packs/{id}` and `GET /acm/total_tls`
  are implemented from Cloudflare's published schema (2026-10-23) and the mock server; run
  `runbook/cloudflare-preflight.sh` (section 10) and `cloudflare-runbook.sh packs` against the
  target zone before relying on them. Whether a Universal pack lists its hosts at pack level or
  only inside `certificates[]` is handled either way.
- **Retiring is one-way and zone-wide for Universal SSL.** The plugin only disables Universal SSL
  when the custom certificate covers every hostname of the Universal pack, but it cannot know about
  hostnames that only Cloudflare features rely on. `enable-universal` in the runbook turns it back
  on (Cloudflare re-orders a Universal certificate, which takes minutes).
- **Free / Pro zones** cannot upload custom certificates at all; the managed certificates are
  discovered but the switch fails at the upload with Cloudflare's plan error.
- **Cloudflare for SaaS custom hostnames** (`mh_custom`, `managed_hostname` packs) and
  **Keyless SSL** are not surfaced and not touched.
