# DigiCert TLM — Fortinet Integrations

Certificate automation for Fortinet appliances driven by **DigiCert Trust Lifecycle Manager (TLM)**.

Two integration styles are provided. They are **alternatives**: a customer picks one per appliance, and they are never run against the same appliance together.

| Style | Runs on | What it does | Where |
|-------|---------|--------------|-------|
| **Admin Web Request post-enrollment script** (AWR) | TLM **Agent** | After TLM issues or renews a certificate, the Agent writes the cert + key to disk and runs a script that deploys them to the appliance via its REST API. The script is configured as a post-enrollment automation on the TLM profile and receives everything through the `DC1_POST_SCRIPT_DATA` environment variable. | `<product>/admin-webrequest-post-script/` (FortiGATE, FortiWEB), `FortiNAC/` |
| **Extensibility custom plugin** | TLM **Sensor** | A Java plugin uploaded to TLM that gives the appliance a first-class connector: it **discovers** the certificates already on the appliance into the TLM inventory, generates the key pair and CSR on the sensor, and installs, repoints and validates the renewed certificate, all from the TLM UI. | `<product>/extensibility-custom-plugins/` (FortiGATE, FortiWEB) |

## Which style to use

| | AWR post-enrollment script | Extensibility custom plugin |
|---|---|---|
| Key pair generated by | TLM (delivered to the Agent with the certificate) | The plugin, on the sensor; the CSR goes to TLM for signing |
| Inventory of existing appliance certificates in TLM | No | Yes (discovery) |
| Appliance onboarding | Script + arguments on the TLM profile | Connector per appliance in the TLM UI |
| Privileged-access (PAM) credential support | No (token is a script argument) | Yes (Secrets Manager connector) |
| Platforms | FortiGate (Linux + Windows), FortiWeb (Linux), FortiNAC (Linux) | FortiGate, FortiWeb (sensor with JDK 17) |
| Code | Bash / PowerShell, no build step | Java, Maven build against the TLM Plugin SDK |

Both styles handle renewal the same way because of how Fortinet appliances behave: **a certificate cannot be overwritten in place** (importing under an existing name is rejected, and a referenced certificate cannot be deleted). Every renewal is therefore a **rotation**: import the new certificate under a new name, repoint every reference, then delete the old certificate once nothing uses it.

## Common prerequisites

- **DigiCert TLM** with either the **TLM Agent** (AWR scripts) or a **TLM Sensor** (plugins) installed on a host that can reach the appliance's management interface.
- An **API token or administrator account** on the appliance with permission to manage certificates and the objects that reference them. Each sub-folder README lists the exact endpoints.
- AWR scripts must have `LEGAL_NOTICE_ACCEPT` set to `"true"` inside the script before they will execute.

Product-specific requirements (bash/python3/curl/openssl versions, PowerShell version, Java/Maven, firmware versions tested) are documented in each sub-folder.
