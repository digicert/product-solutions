# FortiGate — TLM extensibility custom plugin

This folder holds the **custom automation plugin** for **DigiCert Trust Lifecycle Manager (TLM)** that manages the certificate lifecycle on a Fortinet **FortiGate** (FortiOS) from inside TLM, with no script on the Agent side.

The plugin README inside the source folder is the authoritative reference for this plugin. This page explains how a TLM custom automation plugin works, what this one does, and how to build, deploy and operate it.

## What a TLM automation plugin is

TLM's **extensibility** feature lets a customer upload a packaged plugin that TLM runs on one of its **sensors**. Once uploaded, the plugin appears as a new **connector type**: the operator creates one connector per appliance, TLM calls the plugin to discover what is on the appliance, and from then on certificate requests and renewals for that appliance are driven entirely from the TLM UI.

Compared with the Admin Web Request (AWR) post-enrollment script in the sibling folder:

| | AWR post-enrollment script | Extensibility custom plugin |
|---|---|---|
| Runs on | TLM **Agent** (any host that can reach the appliance) | TLM **Sensor** with a JDK 17 runtime |
| Key pair | Generated by TLM, delivered with the certificate | Generated **on the sensor** by the plugin; only the CSR leaves the sensor |
| Existing appliance certificates visible in TLM | No | Yes: discovery populates the TLM inventory, including factory and expired certificates |
| Onboarding | Script copied to the Agent, arguments set on the TLM profile | Connector form in TLM (host, port, credentials, scope); no files on the Agent |
| Credentials | Token or password as a script argument | Stored by TLM as a sensitive field, or resolved at run time from a **Secrets Manager (PAM)** connector |
| Which certificate is replaced | By name convention or subject CN | Resolved from what TLM sends: explicit name → alias → **thumbprint** → endpoint → subject CN + key algorithm |

Both styles rotate rather than overwrite, because FortiGate does not allow a local certificate to be replaced in place over the API: import under an existing name is rejected as a duplicate, and a referenced certificate cannot be deleted.

### The five lifecycle operations

The plugin extends the TLM Plugin SDK's `AbstractAutomationWorkflow` and implements five operations. TLM starts a fresh JVM for each call and passes the request as JSON.

| Operation | What the FortiGate plugin does |
|-----------|-------------------------------|
| `testConnection` | `GET /cmdb/vpn.certificate/local?{scope}&with_meta=1`: proves token, network and certificate read access; logs hostname and firmware from `monitor/system/status` |
| `refreshConfiguration` | Lists `cmdb/vpn.certificate/local` merged with `monitor/system/available-certificates`; fetches each PEM body from `monitor/system/certificate/download`, else the single cmdb entry, else a TLS handshake against a listener; scans SSL-VPN settings, `system/global`, `user/setting`, `system/ftm-push`, IPsec phase1(-interface), firewall VIPs and SSL/SSH profiles for references |
| `generateCsr` | No FortiGate call. Key pair + PKCS#10 CSR generated on the sensor; private key kept in the flow directory |
| `installCertificate` | Resolve the certificate to replace → `POST /monitor/vpn-certificate/local/import` (JSON, base64 cert + key) → `PUT` on every reference → `DELETE /cmdb/vpn.certificate/local/<old>?{scope}` once `q_ref` is 0 |
| `validateCertificate` | Certificate present, not `expired`/`pending`, serial cross-checked against the flow record; returns the leaf PEM recorded at install |

`{scope}` is `scope=global` (default) or `vdom=<name>` depending on the connector's *Certificate scope*.

`generateCsr` and `installCertificate` must run on the **same sensor**, because the private key lives on that sensor between the two calls.

### Rotation model

1. The new certificate is imported as `<sanitised CN>_<last 12 hex digits of the serial>` (for example `vpn_example_com_0a1b2c3d4e5f`). The serial makes the name unique, so a duplicate-name error cannot occur. FortiOS caps names at 35 characters; the CN is truncated to fit.
2. The plugin confirms the name the appliance actually stored by diffing the certificate list before and after the import.
3. It finds every reference to the certificate being replaced and `PUT`s each one to the new name. List-valued fields are rewritten with only the matching member swapped.
4. It re-reads the old certificate and deletes it **only if** it is not a factory certificate and FortiOS reports `q_ref` 0 (read with `with_meta=1`, since the monitor view reports 0 for factory certificates even when referenced). Anything still referenced by an object type the plugin does not scan is left in place with a warning.
5. If any repoint fails, the new certificate stays imported, the old one stays bound, and the install is reported as failed with the list of references that could not be moved. A TLM retry recognises the earlier import (same name, same serial) and re-runs only the rotation.

Reference types scanned: `vpn.ssl/settings` servercert · `system/global` admin-server-cert · `user/setting` auth-cert · `system/ftm-push` server-cert · `vpn.ipsec/phase1` and `phase1-interface` certificate · `firewall/vip` ssl-certificate · `firewall/ssl-ssh-profile` server-cert.

### Which certificate gets replaced

TLM identifies the certificate being renewed in several ways that are not always consistent. The alias it round-trips in `virtualServerName` can be **stale**: TLM keeps the alias it discovered first, while every renewal creates a new object name. `ReplacementResolver` therefore picks the certificate(s) to rotate out through a chain, accepting only names that **exist on the appliance**, and logs which rule matched:

1. an explicit `certificateName` extended-request field (operator override), else
2. the `virtualServerName` alias (`<partition>/<name>`), else
3. the `currentCertificateThumbprint` TLM sends (SHA-256 of the certificate it last saw), matched against the fingerprints and bodies known from discovery, else
4. the **endpoint**: the certificate whose stable discovery endpoint equals the request's `ipAddress`, else
5. **subject match**: certificates whose CN equals the new leaf's CN or one of its SAN DNS names, with the same key algorithm (an RSA renewal never selects an ECC certificate).

If nothing matches, the new certificate is imported and a warning explains that nothing was repointed or deleted.

### Asset discovery and the endpoint model

TLM's automation inventory is endpoint-centric: a certificate is listed only when anchored to an `IP:port`. An appliance certificate may be bound to several listeners or to none, so the plugin synthesises one stable endpoint per certificate from values that survive a renewal:

```
<sanitised CN>-<rsa|ecc|dsa>.<appliance host>:443      e.g. vpn-example-com-rsa.appliance.example.com:443
```

The appliance's object name is round-tripped as the asset **alias**. After a rotation the next discovery shows the same endpoint carrying the new name; the deleted certificate simply stops being listed. TLM only inventories a certificate when it receives the PEM body. FortiOS returns certificate bodies over REST, so no CLI account is needed. On 7.6.7 the download endpoint returned every local certificate, factory-embedded ones included.

## Connector configuration

`configuration.json` defines the connector form TLM shows. Field names matter: TLM maps them onto its own attributes and its PAM injection relies on the credential living in `config_attributes.password`.

| Field | Notes |
|-------|-------|
| Managing sensor | Dynamic list of TLM sensors |
| FortiGate host (FQDN or IP) | Bare host; a scheme, path or `:port` is tolerated and stripped. Declared as `config_attributes.management_ip`. Part of the connector's unique key |
| FortiGate HTTPS admin / REST API port (not SSH) | Default 443. The plugin refuses port 22 with a clear message. Part of the unique key |
| Authentication method | *Self-authentication (Direct input)* (default) or *Self-authentication (Secrets manager)* |
| FortiGate REST API token | Direct input: the token of a FortiGate **REST API administrator**, stored by TLM as a sensitive credential. Secrets manager: the **vault reference** the PAM connector resolves at run time |
| Secrets manager connector | Secrets-manager mode only; dynamic list of registered PAM connectors |
| FortiGate VDOM | Default `root`; the VDOM whose objects are scanned and repointed. Part of the unique key |
| Certificate scope | `global` (default) or `vdom` |
| Replaced certificate after rotation | `delete` (default) or `keep` |

Every field is declared required with a default where one makes sense. This is deliberate: the TLM connector form answered "Server error, see logs for details" on add and edit while fields were declared optional.

### Secrets Manager (PAM) authentication

The connector stores only a **vault reference**; at run time TLM asks the selected PAM connector (BeyondTrust Password Safe, CyberArk CCP, Delinea Secret Server / Platform) to resolve it and injects the real secret into the `password` field. The plugin **fails closed** when no value arrives. Directly typed secrets arrive base64-encoded from TLM and are decoded only when the decoded bytes are printable text.

## FortiGate prerequisites

- **REST API reachable** from the sensor on the HTTPS administrative-access port (default 443).
- A **REST API administrator** (System → Administrators → Create New → REST API Admin) whose **administrator profile** grants Read/Write on *System* (certificates), *VPN* (SSL-VPN settings, IPsec) and *Firewall* (VIPs, SSL/SSH profiles), and whose **trusted hosts** include the sensor's address. The token is shown once at creation and cannot be retrieved afterwards.
- **No SSH / CLI access** is required.
- Multi-VDOM units: use a REST API admin with the right VDOM assignment; global certificates are addressed with `scope=global`.
- Intermediate CA certificates are **not** managed by the plugin: import the DigiCert intermediate once under *System → Certificates → Create/Import → CA Certificate*.

## Building

Requirements: **Java 17+**, **Maven 3.6+**, and access to the DigiCert TLM Plugin SDK on GitHub Packages (`com.digicert.tlm:plugin-sdk:1.1`) plus Maven Central (BouncyCastle, Jackson, SLF4J).

```bash
cd automation-plugins/fortinet-fortigate-certificate-automation
export GITHUB_ACTOR=<your-github-username>
export GITHUB_TOKEN=<token-with-read:packages>
./build.sh           # or: mvn clean package -s settings.xml -U
```

`build.sh` checks the token's scopes before building. Artifacts:

| Artifact | Purpose |
|----------|---------|
| `target/fortigate-automation-plugin-1.0.0.jar` | Fat (shaded) JAR; jar signatures stripped |
| `plugin-dist/fortigate-automation-plugin-1.0.0.zip` | **The file uploaded to TLM**: the JAR plus `plugin-meta.json` |
| `plugin-dist/checksums` | SHA-256 of the ZIP |

`plugin-meta.json` tells the sensor how to launch the plugin on Linux and Windows (`java -jar …`, `JAVA_HOME` from the sensor's `TG_JAVA_HOME`, `PROCESS_TIMEOUT=30m`). The TLM `SdkRuntime` eagerly loads every class in the JAR at start-up, so re-verify the shaded JAR loads cleanly after any dependency change.

`target/` and `plugin-dist/` are git-ignored build outputs.

## Deploying and operating in TLM

1. **Run the runbook first.** `runbook/` contains a curl helper that issues the same API calls as the plugin, in the order TLM triggers them, against a real appliance. `RUNBOOK.md` walks through discovery, CSR, import, repoint, the delete gate and clean-up. Doing this once per firmware version confirms field names and behaviour before anything runs from TLM.
2. **Upload the plugin.** In TLM, add `plugin-dist/fortigate-automation-plugin-1.0.0.zip` as a custom automation plugin under the extensibility / integrations area. TLM distributes it to the sensors.
3. **Create a connector** of the new type: choose the managing sensor and fill in the appliance fields above. *Test Connection* must succeed.
4. **Run discovery.** The appliance's certificates appear in the TLM inventory, one asset per certificate, with the appliance object name as the alias.
5. **Request or renew** a certificate for a discovered asset. TLM calls `generateCsr`, issues the certificate, then calls `installCertificate` and `validateCertificate`. The appliance shows the new uniquely named certificate bound everywhere the old one was, and the old one removed (unless *keep* was selected).

The sensor logs each plugin invocation; the plugin logs every API call with its HTTP status and the appliance's error envelope on failure. Tokens and passwords are never logged.

## Security notes

- **TLS to the appliance is trust-all** with hostname verification disabled, matching `curl -k` in the AWR script, because Fortinet appliances typically run a factory or self-signed management certificate and are addressed by IP. The sensor-to-appliance path should therefore be a trusted management network.
- **Private key custody.** The key pair is generated on the sensor and the PKCS#8 key is written owner-readable (`rw-------`) to `<java.io.tmpdir>/FortiGateAutomationPlugin/<flowId>/request.key` between `generateCsr` and `installCertificate`, then deleted as soon as the import succeeds. On Windows sensors the file inherits the temp directory's ACL.
- **Credentials** are held by TLM as sensitive fields or resolved from PAM at run time; the plugin never logs them.

## Known limitations

- One appliance (and one VDOM / ADOM) per connector.
- CSR and install must run on the same sensor.
- Reference types outside the scanned list are not repointed; the appliance's own refusal to delete a referenced certificate keeps the old one in place.
- Built-in / factory certificates can be replaced as references but are never deleted.
- Verified on FortiOS **7.6.7** (FortiGate VM64-AWS), runbook-validated 2026-09-22 only. Other firmware: run the runbook's discovery step first; the parsers tolerate several field spellings and re-derive X.509 fields from the PEM when available.
- IPsec phase1 / SSL-VPN / SSL-SSH-profile repoints, `certificateScope = vdom` on a multi-VDOM unit, the Secrets Manager path and the full CSR → install → validate sequence driven from TLM have not yet been exercised (the same REST calls succeeded from the runbook; discovery and Test Connection succeeded from TLM).
- SSL-VPN is being retired on some FortiOS 7.6+ models; if `vpn.ssl/settings` is absent the scan logs it and moves on.
